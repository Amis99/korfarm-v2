1.1 현재 동작 정리

사용자 유형셀프 재설정 (잊었을 때)어드민 강제 재설정로그인 후 본인 변경
학생 (STUDENT) ❌ /reset UI 만 있고 백엔드 무동작 ❌ endpoint 미존재 ✅ PUT /v1/auth/me password 필드 — oldPassword 검증 X
학부모 (PARENT) ❌ 동일 ❌ endpoint 미존재 ✅ 동일 — oldPassword 검증 X
기관 관리자 (ORG_ADMIN) ❌ 동일 ❌ endpoint 미존재 ✅ 동일 — oldPassword 검증 X
본사 관리자 (HQ_ADMIN) ❌ 동일 ✅ POST /v1/admin/hq/{userId}/reset-password (HQ_ADMIN→HQ_ADMIN 만) ✅ 동일 — oldPassword 검증 X

1.2 발견된 문제

P0 oldPassword 검증 누락 — 계정 탈취 위험

UpdateProfileRequest.password (ApiDtos.kt:51) 필드가 그대로 passwordHash 갱신. AuthService.updateProfile (AuthService.kt:290-292): request.password?.let { if (it.length >= 8) user.passwordHash = passwordEncoder.encode(it) }. 현재 비밀번호 확인 단계가 없음.

  • JWT 토큰 탈취 또는 XSS 로 sessionStorage 의 token 유출 시 → 즉시 비번 변경 가능 → 영구 계정 탈취.
  • 모든 사용자 유형(학생·학부모·기관·본사 관리자) 공통 노출.
  • 일반적 패턴: oldPassword 검증 + 새 비번 변경 endpoint 분리 (예: POST /v1/auth/change-password).

P1 실질적 셀프 비밀번호 찾기 기능 없음

/reset 페이지 → POST /v1/auth/request-password-reset 호출 → 백엔드(AuthController.kt:132-141) 가 userRepository.existsByEmail 호출 후 결과 무시, 무조건 같은 안내 메시지 응답: 

"message" to "비밀번호 초기화 요청이 접수되었습니다. 선생님 또는 관리자에게 문의하세요."
  • 이메일 발송 X · 임시 비번 발급 X · 토큰 발급 X. UI 만 있고 실제 동작 0.
  • 사용자가 안내문 그대로 "선생님 또는 관리자에게 문의" 해야 함 — 셀프 회복 불가.
  • UI 헤더 "본인 확인 후 재설정 안내를 받을 수 있어요" 표현이 실제와 다름. misleading.

P1 어드민의 학생·학부모·기관 비번 재설정 endpoint 부재

HQ_ADMIN 의 POST /v1/admin/hq/{userId}/reset-password 는 본사 관리자(HQ_ADMIN) 만 대상. requireHqMembership(userId) 가드로 다른 유형 차단.

  • 학생이 비번 잊었을 때 ORG_ADMIN 또는 HQ_ADMIN 이 reset 할 백엔드 endpoint 자체가 없음.
  • 운영 임시 처방: 어드민이 RDS 직접 UPDATE 또는 DB 콘솔 접근 — 운영 부담 + 사고 위험.
  • OrgService 의 학생/관리자 생성 시점에는 평문 임시 비번 응답이 있으나 사후 재설정 경로는 없음.

P2 이메일·SMS 인증 인프라 부재

  • 임시 비번 발송 채널 없음. 토큰 발급 + URL link + 만료 정책 없음.
  • 비번 재설정 안전성·UX 의 기반 인프라. 도입 시 SMTP/SendGrid · 인증번호 관리 테이블 등 필요.
  • 장기 과제. 단기는 어드민 강제 재설정 endpoint 로 운영 가능.

P2 임시 비밀번호 평문 API 응답

HqAdminController.resetPassword 응답에 평문 임시 비번 포함 ("tempPassword": "..." , "message": "임시 비밀번호: ..."). OrgService 의 학생 생성 응답도 동일.

  • 어드민이 본인에게 직접 전달용 의도. 운영 정책으로 인정.
  • 다만 API 응답·서버 로그·HTTP 캐시·중간 프록시 등에 평문 노출 가능. 운영 로그 마스킹 권장.
  • 장기 개선: 임시 토큰 URL 발급 + 한 번 사용 후 만료 패턴.

OK 계정 열거 공격 방지

request-password-reset 가 존재 여부와 무관하게 같은 응답 반환 — 의도된 동작. OK. 다만 existsByEmail 호출이 결과 사용 없어 무의미 (제거 가능).

운영 활성화 절차

  1. SMTP 계정 발급 (예: SendGrid·AWS SES·Gmail SMTP 등) 또는 회사 메일 서버 정보 확보.
  2. EC2 환경변수 추가: MAIL_HOST, MAIL_PORT(기본 587), MAIL_USERNAME, MAIL_PASSWORD, MAIL_FROM, PASSWORD_RESET_LINK_BASE(기본 https://googerfarm.com/reset).
  3. 백엔드 재기동. 환경변수 없으면 발송 skip + 로그만 출력 → 운영에 무해.

회귀 점검

  • ✅ SecurityConfig 의 /v1/auth/** permitAll 패턴에 새 endpoint 모두 자동 포함.
  • ✅ 계정 열거 방지 — 미존재 계정 요청도 응답 동일.
  • ✅ 토큰 발송 실패해도 외부 응답 동일 (운영자가 어드민 재설정으로 우회 가능).
  • ✅ Spring Mail Starter 의존성 추가 — JavaMailSender Bean 은 mail.host 가 있어야 활성. JavaMailSender? nullable 으로 받아 미설정 시 null 안전.
