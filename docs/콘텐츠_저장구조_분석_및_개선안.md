## 1. 현재 문제 데이터 저장 위치 종합

### 1.1 한눈에 보기

| 유형 | 주 저장소 | 위치 | 규모 |
|------|----------|------|------|
| **일일 퀴즈** | 프론트엔드 정적 JSON | `frontend/public/daily-quiz/` | 4,392개 파일 (12레벨 × 366일) |
| **일일 독해** | 프론트엔드 정적 JSON | `frontend/public/daily-reading/` | 4,380개 파일 (12레벨 × 365일) |
| **대결 모드** | 백엔드 DB | `duel_question_pool` 테이블 | 초기 200문제 (SQL 시드) |
| **농장 모드** | 프론트엔드 정적 JSON | `frontend/public/farm/` | 14개 파일 (9카테고리) |
| **프로 모드** | DB(구조) + 정적 JSON(콘텐츠) | DB: `pro_chapters`/`pro_chapter_items`, 문제: `frontend/public/farm/` 재활용 | 챕터 구조는 DB, 문제는 농장 JSON 공유 |

### 1.2 일일 퀴즈

**경로**: `frontend/public/daily-quiz/{레벨}/{001~366}.json`

```
daily-quiz/
├── saussure1/   (001.json ~ 366.json)  ← 초1
├── saussure2/                           ← 초2
├── saussure3/                           ← 초3

- **참조 코드**: `DailyQuizPage.jsx` → 사용자의 학습 시작일 기준 `dayIndex` 계산 후 해당 JSON을 `fetch()`
- **백엔드 역할**: 결과 기록만 (`farm_learning_logs` 테이블). `LearningService.getDailyQuiz()`는 스텁 데이터만 반환

```

- **참조 코드**: `DailyReadingPage.jsx` → 일일 퀴즈와 동일 방식으로 `dayIndex` 기반 fetch
- **백엔드 역할**: 결과 기록만

### 1.4 대결 모드 — 유일하게 백엔드 DB 기반

**DB 테이블**: `duel_question_pool`

```sql
CREATE TABLE duel_question_pool (
  id VARCHAR(64) PRIMARY KEY,
  server_id VARCHAR(32),       -- saussure, frege, russell, wittgenstein
  question_type VARCHAR(32),   -- QUIZ, READING
  category VARCHAR(32),        -- VOCAB, BACKGROUND, CONCEPT, SENTENCE, DETAIL
  question_json JSON,          -- 문제 전체 (stem, choices, answerId, timeLimitSec)
  status VARCHAR(16) DEFAULT 'ACTIVE'
);
```

- **초기 시드**: `backend/src/main/resources/db/seed_duel_questions.sql` (200문제)
- **추가 임포트**: 루트의 `*-batch*.json` 파일 → 관리자가 수동으로 복사-붙여넣기 → `POST /v1/admin/duel/questions/import`
- **사용 코드**: `DuelQuestionPoolService.kt` → 서버별 QUIZ 6문제 + READING 4문제 = 10문제 랜덤 선정

#### 루트 batch JSON 파일 (대결 문제 임포트용)

```
루트/
├── frege-batch1~5-*.json      (25개 파일)
├── russ-batch1~5-*.json       (25개 파일)
├── saussure-batch1~5-*.json   (25개 파일)
└── witt-batch1~5-*.json       (25개 파일)
```

각 배치 구성:
- batch1: 문법 + 어휘
- batch2: 문학감상 + 문학기법
- batch3: 배경지식 + 논리
- batch4: 비문학 독해
- batch5: 문학 독해

코드에서 직접 import하지 않으며, 관리자가 파일 내용을 관리자 페이지에 붙여넣어 DB에 저장하는 방식이다.

### 1.6 프로 모드 — 하이브리드 (DB 구조 + 정적 JSON 콘텐츠)

**DB 테이블 (구조)**:
- `pro_chapters`: 챕터 목록 (레벨별 순서)
- `pro_chapter_items`: 챕터별 아이템 (reading/vocab/background/logic/answer/test)
- `pro_progress`: 사용자별 완료 기록

**문제 데이터**: `frontend/public/farm/` 의 농장 모드 JSON을 재활용

**흐름**:
1. `ProModePage.jsx` → `GET /v1/pro/chapters` (DB에서 챕터 목록)
2. `ProChapterPage.jsx` → `GET /v1/pro/chapters/{id}/items` (DB에서 아이템 목록)
3. 아이템 클릭 → `LearningRunnerPage.jsx` → `learningCatalog.js`에서 `contentId` 매칭 → `farm/` 하위 JSON fetch

## 2. 현재 구조의 문제점

### 2.1 `frontend/public/`에 정적 파일로 넣는 방식의 한계

| 문제 | 설명 |
|------|------|
| **배포 결합** | 콘텐츠 1개 추가/수정할 때마다 프론트엔드 전체를 다시 빌드·배포해야 한다 |
| **접근 제어 불가** | `public/` 파일은 URL만 알면 누구나 접근 가능하다. 유료 콘텐츠도 노출된다 |
| **빌드 시간 증가** | 수만 개 JSON이 빌드 파이프라인에 포함되면 Vite 빌드/Amplify 배포가 느려진다 |
| **카탈로그 하드코딩** | `learningCatalog.js`에 항목을 수동 등록해야 하므로 수만 개 관리가 불가능하다 |
| **레벨별 구분 없음** | 농장 모드 JSON 14개가 레벨 구분 없이 하나씩만 존재한다 (실제론 12레벨 × 14종 = 168개 이상 필요) |

### 2.2 이중 저장 구조의 혼란

```
현재 데이터 흐름이 꼬여 있다:

관리자 → DB (contents + content_versions)에 업로드  ← 사용 안 됨
프론트 → public/farm/ 정적 JSON에서 직접 fetch      ← 실제 사용

프로 모드:
  챕터 구조 → DB에서 API로 조회
  실제 문제 → learningCatalog.js → public/farm/ JSON fetch

  → DB에 콘텐츠를 넣어도 프론트가 안 쓴다
```

### 2.3 확장 시 예상 규모

| 유형 | 현재 | 서비스 목표 규모 |
|------|------|-----------------|
| 일일 퀴즈 | 4,392개 | 12레벨 × 366일 = 4,392개 (현재와 동일) |
| 일일 독해 | 4,380개 | 12레벨 × 365일 = 4,380개 (현재와 동일) |
| 농장 모드 | 14개 (레벨 무관) | 12레벨 × 9농장 × 수십 세트 = **수천 개** |
| 프로 모드 | 14개 재활용 | 12레벨 × 20장 × 4~6아이템 = **960~1,440개** |
| 대결 모드 | 200개 (DB) | 12레벨 × 수백 개 = **수천 개** (이미 DB 기반) |
| **합계** | ~8,800개 | **수만 개** |

## 3. 권장 구조: 백엔드 DB 기반 단일 콘텐츠 서빙

### 3.1 핵심 원칙

**콘텐츠는 백엔드가 관리하고, 프론트엔드는 API로 받아서 렌더링만 한다.**

```
┌─────────────────────────────────────────────────────────┐
│  관리자 콘솔                                              │
│  JSON 업로드 → POST /v1/admin/content/import             │
└──────────────────────┬──────────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────────┐
│  백엔드 DB (단일 진실의 원천)                              │
│                                                          │
│  contents (메타)  ←→  content_versions (JSON 본문)       │
│    content_type        content_json (JSON 컬럼)          │
│    level_id            schema_version                    │
│    area, sub_area      uploaded_by                       │
│    status              created_at                        │
│    day_index (일일용)                                     │
│                                                          │
│  → 이미 테이블이 존재한다. 지금은 안 쓰고 있을 뿐         │
└──────────────────────┬──────────────────────────────────┘
                       │ API
                       ▼
┌─────────────────────────────────────────────────────────┐
│  프론트엔드                                               │
│                                                          │
│  learningCatalog.js 삭제 (하드코딩 제거)                  │
│  public/farm/ 삭제 (정적 JSON 제거)                       │
│  public/daily-quiz/ 삭제                                  │
│  public/daily-reading/ 삭제                               │
│                                                          │
│  → 모든 콘텐츠를 API로 요청                               │
│     GET /v1/content/{contentId}                          │
│     GET /v1/daily-quiz?level=russell1&day=42             │
│     GET /v1/farm/catalog?farmId=vocab&level=russell1     │
└─────────────────────────────────────────────────────────┘
```

### 3.2 API 설계

```
# 카탈로그 조회 (learningCatalog.js 대체)
GET /v1/farm/catalog?farmId=vocab&level=RUSSELL_1
→ [{ contentId, title, contentType, moduleKey, subArea }, ...]

# 콘텐츠 본문 조회 (public/farm/ JSON 대체)
GET /v1/content/{contentId}
→ { contentId, contentType, payload: { questions: [...] } }

# 일일 퀴즈 (public/daily-quiz/ 대체)
GET /v1/daily-quiz?level=RUSSELL_1&dayIndex=42
→ { contentId, payload: { ... } }

# 일일 독해 (public/daily-reading/ 대체)
GET /v1/daily-reading?level=RUSSELL_1&dayIndex=42
→ { contentId, payload: { ... } }

# 프로 모드 (이미 DB 기반이므로 contentId 연결만 수정)
GET /v1/pro/chapters/{chapterId}/items/{itemId}/content
→ { contentId, payload: { ... } }
```

### 3.3 DB 구조 변경 (기존 테이블 활용)

```sql
-- contents 테이블에 필드 추가
ALTER TABLE contents ADD COLUMN area VARCHAR(32);       -- VOCAB, READING, GRAMMAR...
ALTER TABLE contents ADD COLUMN sub_area VARCHAR(32);   -- BASIC, NONFICTION...
ALTER TABLE contents ADD COLUMN day_index INT;          -- 일일 퀴즈/독해용 (1~366)
ALTER TABLE contents ADD COLUMN module_key VARCHAR(64); -- worksheet_quiz, reading_training...

-- 인덱스 추가
CREATE INDEX idx_contents_daily ON contents(content_type, level_id, day_index);
CREATE INDEX idx_contents_farm ON contents(content_type, level_id, area);
```

contents 테이블 예시:

```
┌──────────────┬──────────────┬──────────┬──────┬───────────────┬──────────┐
│ content_type │ level_id     │ area     │ day  │ module_key    │ status   │
├──────────────┼──────────────┼──────────┼──────┼───────────────┼──────────┤
│ DAILY_QUIZ   │ RUSSELL_1    │ GENERAL  │ 1    │ worksheet_quiz│ PUBLISHED│
│ DAILY_QUIZ   │ RUSSELL_1    │ GENERAL  │ 2    │ worksheet_quiz│ PUBLISHED│
│ VOCAB_BASIC  │ RUSSELL_1    │ VOCAB    │ NULL │ worksheet_quiz│ PUBLISHED│
│ VOCAB_BASIC  │ FREGE_1      │ VOCAB    │ NULL │ worksheet_quiz│ PUBLISHED│
│ ...          │ ...          │ ...      │ ...  │ ...           │ ...      │
└──────────────┴──────────────┴──────────┴──────┴───────────────┴──────────┘

content_versions 테이블: content_json 컬럼에 실제 문제 JSON 저장
```

## 4. 마이그레이션 전략 (기존 JSON → DB)

한 번에 바꿀 필요 없이 단계적으로 진행한다.

### 4.1 1단계: 농장 모드 (14개 → DB)

- 가장 적은 양이라 먼저 전환한다
- 관리자 콘솔의 import API가 이미 존재한다
- `LearningRunnerPage.jsx`에서 `fetch(jsonPath)` → `apiGet(/v1/content/${contentId})` 변경
- `learningCatalog.js` → `GET /v1/farm/catalog` API로 대체

### 4.2 2단계: 프로 모드 연결 정리

- `ProChapterItem.contentId`가 DB의 `contents.id`를 직접 가리키도록 변경
- 이미 DB 구조가 있으므로 프론트엔드 수정만 필요

### 4.3 3단계: 일일 퀴즈/독해 (8,700개 → DB)

- Python 스크립트로 기존 JSON 파일을 일괄 import
- `public/daily-quiz/`, `public/daily-reading/` 삭제
- 프론트엔드 빌드 크기 대폭 감소

### 4.4 4단계: 캐싱 최적화

- 일일 콘텐츠는 하루 동안 불변 → Redis 또는 HTTP 캐시 헤더 활용
- `Cache-Control: public, max-age=86400` 으로 CDN 캐싱

## 5. 현재 vs 권장 비교

| 항목 | 현재 | 권장 |
|------|------|------|
| **콘텐츠 저장** | `frontend/public/` 정적 파일 | 백엔드 DB (`contents` + `content_versions`) |
| **카탈로그** | `learningCatalog.js` 하드코딩 | API로 동적 조회 |
| **콘텐츠 추가** | JSON 파일 배치 + 코드 수정 + 재배포 | 관리자 콘솔에서 업로드 (재배포 불필요) |
| **접근 제어** | 없음 (URL 노출) | JWT + 구독 확인 후 서빙 |
| **확장성** | 파일 수 증가 → 빌드 느려짐 | DB 쿼리로 무한 확장 |
| **콘텐츠 수정** | JSON 파일 수정 + 재배포 | 관리자 콘솔에서 수정 (버전 관리 자동) |
| **콘텐츠 검색** | 불가 | content_type, level_id, area 등으로 검색 |

## 6. 결론

DB 기반 구조는 이미 백엔드에 만들어져 있다 (`contents`, `content_versions` 테이블 + `AdminContentService`). 문제는 프론트엔드가 이걸 안 쓰고 정적 파일을 직접 fetch하고 있다는 것이다. 프론트엔드의 데이터 로딩 경로만 API로 바꾸면 수만 개도 문제없이 관리할 수 있다.
