# 전체 프로젝트 기능 점검 보고서

점검일: 2026-04-24 19:21 KST  
대상: 국어농장 v2 전체 저장소  
방식: 소스/설정/마이그레이션 정적 점검, 프론트/백엔드 빌드 검증, AWS 인증 확인, 운영 DB 스키마 메타데이터 확인

## 요약

- 프론트엔드는 React 19 + Vite 7 구조이며, 라우터 기준 112개 경로, `pages` 106개, JSX 컴포넌트 90개 규모다.
- 백엔드는 Spring Boot 3.2 + Kotlin 구조이며, Kotlin 파일 217개, REST 컨트롤러 53개, HTTP 매핑 345개 규모다.
- DB 마이그레이션은 SQL 65개 파일, `CREATE TABLE` 90개를 포함한다. JPA `@Table` 매핑은 97개로, 마이그레이션만으로 재현되지 않는 엔티티 테이블 13개가 있다.
- 프론트 프로덕션 빌드와 백엔드 `test`, `bootJar`는 통과했다.
- 프론트 ESLint는 실패했다. 현재 설정이 `public` 아래 생성/보정 스크립트까지 검사하고 있고, `src`에도 React 19 훅 규칙, 미사용 변수, 중복 키 문제가 남아 있다.
- AWS CLI 인증은 가능하다. 다만 STS 결과가 root ARN으로 확인되어 운영 자동화에는 최소 권한 IAM 사용자/역할로 분리하는 것이 맞다.
- 운영 DB는 SSH 터널로 연결되었고, 마이그레이션 누락 후보 테이블은 현재 DB에 존재한다. 즉 기존 운영 DB는 살아 있지만, 새 DB를 마이그레이션만으로 재구성하는 능력은 부족하다.

## 주요 발견 사항

### P0. 마이그레이션만으로 새 DB를 재현할 수 없음

JPA 테이블 매핑 97개 중 13개는 마이그레이션의 `CREATE TABLE`에 없다.

- 누락 후보: `learning_streaks`, `pro_chapter_items`, `pro_chapter_tests`, `pro_chapters`, `pro_progress`, `pro_test_sessions`, `test_questions`, `test_submissions`, `wisdom_attachments`, `wisdom_comments`, `wisdom_feedback`, `wisdom_likes`, `wisdom_posts`
- 관련 엔티티: `backend/src/main/kotlin/com/korfarm/api/pro/ProEntities.kt`, `backend/src/main/kotlin/com/korfarm/api/test/TestEntities.kt`, `backend/src/main/kotlin/com/korfarm/api/wisdom/WisdomEntities.kt`, `backend/src/main/kotlin/com/korfarm/api/learning/LearningEntities.kt`
- 관련 마이그레이션은 생성 없이 `ALTER/UPDATE/INSERT`를 수행한다. 예: `V0018`, `V0019`, `V0024`, `V0025`, `V0037`, `V0038`, `V0048`, `V0049`
- 로컬 설정은 `ddl-auto: update`, Flyway off라 누락이 가려진다. 운영 설정은 `ddl-auto: validate`, Flyway on이다.

운영 DB 메타데이터 조회 결과 위 누락 후보 테이블은 현재 DB에 존재하고, `flyway_schema_history`는 최근 `0060`~`0064`가 성공 상태다. 따라서 지금 운영 DB는 수동/과거 생성 이력이 보완하고 있지만, 신규 환경/복구/스테이징을 마이그레이션만으로 만들면 깨질 수 있다.

### P1. 농장 학습 진행 모달이 없는 API를 호출함

`frontend/src/pages/FarmListPage.jsx:168`에서 `/v1/learning/farm/page-progress`를 호출한다. 하지만 `FarmLearningController`에는 `/history`, `/daily-seed-status`, `/start`, `/complete`, `/progress`만 있다.

또 `V0040__content_page_progress.sql`에서 `content_page_progress`를 만들었다가 `V0046__study_content_module.sql:90`에서 `DROP TABLE IF EXISTS content_page_progress`로 제거한다. 프론트가 과거 콘텐츠 페이지 진행률 모델을 계속 호출하는 상태로 보인다.

영향: 농장 목록에서 진행률 모달을 열 때 상세 페이지 진행률이 오류 상태로 떨어진다.

### P1. 운영 자격 증명 관리가 위험함

- `aws sts get-caller-identity` 결과가 root ARN으로 확인된다. 배포 자동화에는 root 계정 대신 S3/CloudFront/EC2 배포에 필요한 최소 권한 IAM 역할 또는 사용자를 써야 한다.
- 여러 `scripts` 파일에 운영 DB/EC2 접근 정보가 직접 들어 있다. 비밀번호 값은 문서에 기록하지 않았지만, `scripts/import-pro-content.js` 등은 환경변수/시크릿 파일 기반으로 바꾸는 것이 맞다.

영향: 로컬 작업자/다른 AI/스크립트 실행 권한이 운영 전체 권한으로 확대될 수 있다.

### P2. 기능 플래그 관리자 페이지가 라우터에 연결되지 않음

`frontend/src/pages/AdminFlagsPage.jsx`는 존재하고 `/v1/admin/flags`를 호출한다. 백엔드도 `AdminFlagController`가 `/v1/admin/flags`를 제공한다. 하지만 `frontend/src/App.jsx`의 관리자 라우트에는 `/admin/flags`가 없다.

영향: 기능 플래그 UI가 빌드에는 포함되지 않거나 직접 접근 불가 상태다. 관리자 메뉴/라우트를 추가하거나 미사용 페이지를 제거해야 한다.

### P2. 프론트 린트 기준이 현재 코드베이스와 맞지 않음

`npm.cmd run lint` 결과: 241 errors, 57 warnings.

주요 유형:

- `frontend/public/**/_tools` 및 임시 생성 스크립트가 브라우저 ESLint 규칙으로 검사되어 `require`, `__dirname`, `process` 오류 발생
- React 19 훅 규칙 오류: `setState` in effect, purity/ref access 등
- 실제 코드 오류 후보: `frontend/src/components/editor/EditorShell.jsx`의 `BACKGROUND_KNOWLEDGE_QUIZ` 중복 키, 여러 미사용 변수

빌드는 통과하지만 린트가 CI 게이트라면 현재 상태로는 배포 전 검증 실패다.

### P2. API/데이터 모델 문서가 현재 구현보다 많이 오래됨

`docs/api.md`는 “API 스켈레톤”이며 실제 345개 HTTP 매핑보다 훨씬 작다. `docs/프로젝트_현황_명세서.md`는 2026-02-05 기준 63개 페이지라고 쓰지만, 현재 라우터는 112개 경로다.

영향: 운영/인수인계/테스트 케이스 작성 시 문서 기반 판단이 틀릴 수 있다.

### P3. 배포는 가능하지만 현재 워크트리 그대로 배포하면 다른 작업까지 포함됨

프론트 배포 스크립트는 `scripts/deploy-frontend.sh`이고 S3 버킷은 `korfarm-frontend`, CloudFront Distribution ID는 문서/로컬 설정에서 확인된다. 백엔드 배포 스크립트는 `scripts/deploy-backend.sh`이고 EC2 호스트/키 경로도 로컬 설정에 남아 있다.

현재 저장소는 다른 AI 작업으로 변경/미추적 파일이 매우 많다. 배포 명령을 실행하면 “우리 변경분만”이 아니라 현재 파일시스템 상태 전체가 빌드/업로드될 수 있다. 배포 전에는 배포 대상 변경 범위를 별도로 고정해야 한다.

## 권장 작업 순서

1. DB 마이그레이션 재현성 복구: 누락 13개 테이블의 기준 DDL을 별도 마이그레이션으로 정리하고, 빈 MySQL DB에서 Flyway + `ddl-auto=validate`를 통과시키기.
2. 농장 `page-progress` 처리 결정: 프론트 호출 제거/대체 또는 백엔드 API 재구현. `content_page_progress`를 제거한 설계라면 프론트 모달도 새 진행률 모델로 바꿔야 한다.
3. root AWS/하드코딩 DB 비밀번호 제거: 배포 전용 IAM 권한, `.env`/Secret Manager/로컬 비공개 설정으로 분리.
4. ESLint 범위 정리: `public` 생성 스크립트를 ignore하거나 Node globals 별도 override를 두고, `src`의 실제 오류를 우선 정리.
5. `AdminFlagsPage` 라우트/메뉴 연결 여부 결정.
6. `docs/api.md`, `docs/data-model.md`, `docs/프로젝트_현황_명세서.md`를 현재 112개 라우트/345개 API 기준으로 갱신.
7. 배포는 현재 더러운 워크트리 정리 또는 명시적 배포 브랜치/커밋 확인 후 진행.
